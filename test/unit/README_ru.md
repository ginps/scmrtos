Юнит‑тесты scmRTOS
==================

([English version](README.md))

Тесты ядра, сервисов и расширений scmRTOS: 261 сценарный тест и несколько
дополнительных уровней проверки (см. «Уровни проверки»). Тесты запускаются на
Linux через тестовый порт `port/linux/gcc`. Сценарные тесты работают в режиме
ручных тиков, поэтому их результат детерминирован с точностью до тика и до
порядка переключений.

Запуск
------

```sh
test/unit/run.sh                 # все уровни, 41 запуск (≈2 минуты)
FUZZ_SEEDS=0 test/unit/run.sh    # без перебора seed-ов
test/unit/run.sh mutex channel   # только тесты, в имени которых есть "mutex" или "channel"
test/unit/run.sh -v              # с выводом и для прошедших тестов
test/unit/coverage.sh            # покрытие строк и ветвей по всем конфигурациям
test/unit/coverage.sh --uncovered --branches   # плюс список непокрытого
```

Один бинарник:

```sh
test/unit/build.sh /tmp/ut -DscmRTOS_CONTEXT_SWITCH_SCHEME=1
/tmp/ut -l                       # список тестов
/tmp/ut kernel.sleep             # фильтр по подстроке
/tmp/ut --seeds=1-300 fuzz.injected   # тест с каждым seed-ом из диапазона
/tmp/ut --seed=34 -v fuzz.single      # повторить один seed с выводом
/tmp/ut -x                       # остановиться на первом неожиданном провале
```

Переменные окружения: `SRC` — дерево scmRTOS для проверки (по умолчанию то,
в котором лежат тесты), `PORT` — каталог порта Linux, `CXX` — компилятор,
`OPT` — оптимизация (по умолчанию `-O1`), `FUZZ_SEEDS` — число seed‑ов на
фаззинг‑тест (по умолчанию 300).

Набор подстраивается под дерево. Если в `SRC` нет develop‑расширений
(semaphore, event-flags, launch, safe-run, watchdog), их тесты и develop‑API
(`try_push`, `terminate(func)`, `process_profiler`) пропускаются. Поэтому тот
же набор проверяет и v5.2.0: `SRC=/path/to/v5.2.0 test/unit/run.sh`.

Уровни проверки
---------------

`run.sh` собирает и запускает всё перечисленное для каждой пары «схема
переключения 0/1 × порядок приоритетов 0/1»:

| Уровень | Программа | Что даёт | Запусков |
| --- | --- | --- | --- |
| Сценарные тесты | основная, перезапуск процессов выкл./вкл. | точный порядок переключений и номера тиков; 254 / 261 тестов | 8 |
| Перебор точек вытеснения | основная, `fuzz.injected_*`, `fuzz.no_injection` | случайная нагрузка из пяти процессов; прерывания подаются при выходе из критических секций; 300 seed‑ов на тест | 4 |
| Одно прерывание в каждой точке | основная, `fuzz.single_interrupt_at_every_point` | фиксированный сценарий, 653 точки × 3 вида прерывания = 1959 запусков | 4 |
| Асинхронный стресс | основная, `fuzz.async_stress`, набор `atomic` | прерывания от настоящего таймера на любой инструкции | в тех же запусках |
| `OS::launch()` | `LAUNCH=1`, C++17, 3 процесса | 6 тестов | 4 |
| Число процессов | `WIDE=N` для N = 1, 7, 8, 15, 16, 31 | границы типа `TProcessMap` и полностью заполненные карты; по 8 тестов | 24 |
| Таблица масок | `-DscmRTOS_LINUX_PRIO_MASK_TABLE=1`, только схема 0 и порядок 0 | `get_prio_tag()` как в портах AVR/MSP430/STM8 (дефект 3) | 1 |

Отдельно запускаются:

| Уровень | Команда | Что даёт |
| --- | --- | --- |
| Санитайзеры | `build.sh /tmp/ut -fsanitize=undefined` или `-fsanitize=address` (для ASan: `ASAN_OPTIONS=detect_stack_use_after_return=0`) | неопределённое поведение и выходы за границы; на develop сообщают только об известных N3 и N4 |
| 16‑битные цели | `test/target16/run.sh` (нужен clang с целями msp430 и avr) | код карт процессов компилируется для настоящей 16‑битной цели, компилятор сворачивает его в константы, они сверяются с ожидаемыми (дефект 1) |
| Мутационное тестирование | `mutate.py`, см. ниже | измеряет, какую долю внесённых в код ошибок тесты замечают |
| Покрытие | `coverage.sh` | строки и ветви |

### Фаззинг с подачей прерываний

Порт вызывает хук при каждом выходе из внешней критической секции, то есть в
каждой точке, где реальный контроллер принял бы ожидающее прерывание. Хук по
случайному закону подаёт системный тик или пользовательское прерывание.
Последовательность зависит только от seed‑а, поэтому любой провал повторяется
командой `--seed=N`. Пять процессов работают с двумя мьютексами, каналом, флагом,
сообщением и семафором и всё время проверяют инварианты: взаимоисключение,
порядок и сохранность элементов канала, предел семафора, минимальную
длительность `sleep()` и таймаутов, завершение всех процессов.

`fuzz.async_stress` и набор `atomic` используют настоящий таймер: прерывание
приходит на произвольной инструкции. Они не воспроизводимы по seed‑у, зато
замечают отсутствующую критическую секцию. На правильном коде они проходят
всегда; ошибку ловят с вероятностью, а не наверняка.

Перебор seed‑ов останавливается после пяти провалов: зависший seed стоит 5 секунд.

### Проверки состояния прерываний

- Фреймворк проверяет в хуке переключения контекста, что планировщик вызван
  с запрещёнными прерываниями.
- Тесты `*_copied_only_inside_critical_sections` используют тип элемента,
  который отмечает каждое своё копирование вне критической секции.
- Порт завершает программу, если процесс перезапускается вне критической секции.

Известные дефекты
-----------------

Тест, помеченный `UT_TEST_DEFECT(..., "id")`, проверяет правильное поведение
там, где оно нарушено известным дефектом. Его провал показывается как
`[ KNWN ]` и не считается ошибкой. Если такой тест прошёл, он отображается как
`[ FIXD ]` (дефект не воспроизвёлся). Номера дефектов — из отчётов по анализу
v5.2.0 (1–15) и ветки develop (N1–N9).

| Дефект | Тесты | v5.2.0 | v5.2.0 + патчи 1–6 | develop |
| --- | --- | --- | --- | --- |
| 2 — потеря таймаута канала | 1 + фаззинг | воспроизводится | исправлен | исправлен |
| 3 — `pssSuspended` и таблица масок | 1, только конфигурация `masktable` | воспроизводится | исправлен | воспроизводится |
| 4 — `Size` больше индекса | 1 | воспроизводится | исправлен (ошибка компиляции) | воспроизводится |
| 5 — переполнение `operator[]` | 2 | воспроизводится | исправлен | воспроизводится |
| 6 — таймаут `try_lock` перезапускается | 2 | воспроизводится | исправлен | воспроизводится |
| N1 — `try_pop_back` наоборот | 2 | — | — | воспроизводится |
| N3 — watchdog и `nullptr` | 2 | — | — | воспроизводится |
| N4 — деление на ноль в профайлере | 2 (в v5.2.0 — 1) | воспроизводится (`TProfiler`) | воспроизводится | воспроизводится |

| N7 — `force_wake_up()` оставляет метку в карте ожидания | 2 | воспроизводится | воспроизводится | воспроизводится |
| N8 — round‑robin будит первый процесс | 1 | воспроизводится | воспроизводится | воспроизводится |
| N9 — `os_running()` до конструктора ядра | 1 | воспроизводится | воспроизводится | воспроизводится |

Дефект N4 затрагивает не только `process_profiler`, но и `TProfiler`,
который есть ещё в v5.2.0. Дефект 1 (16‑битные маски) на 64‑битном хосте не
проявляется; его проверяет `test/target16/run.sh`. На дереве с дефектом 2
фаззинг‑тесты помечаются как известный дефект: они находят его за несколько
seed‑ов.

Итог на основной программе: develop — 15 известных дефектов (16 с таблицей
масок), v5.2.0 — 11–12, v5.2.0 с патчами 1–6 — 5; неожиданных провалов нет.

Покрытие
--------

`coverage.sh` собирает все конфигурации с `--coverage -O0 -fno-exceptions
-DINLINE=inline`. `INLINE=inline` нужен, чтобы функции не встраивались
принудительно: иначе gcov считает ветви каждой встроенной копии отдельно.
`-fno-exceptions` — потому что ядро не использует исключения. Данные всех
конфигураций объединяются: строка покрыта, если её выполнила хотя бы одна.

| Файлы | Строки | Ветви |
| --- | --- | --- |
| ядро (`core/`) | 511/511 — 100% | 131/132 — 99,2% |
| расширения (`ext/`) | 360/368 — 97,8% | 164/174 — 94,3% |
| всего, вместе с портом | 996/1016 — 98,0% | 333/358 — 93,0% |

Покрытие считается по основной программе и `launch`; программы `wide` и
перебор seed‑ов в него не входят.

Непокрытое в ядре и расширениях:

- повтор цикла ожидания в `TKernel::sched()` (схема 1) — порт переключает
  контекст сразу при первом разрешении прерываний;
- вечные циклы, которыми `launch` и watchdog останавливают систему при ошибке;
- защитные условия, недостижимые через публичный API (`safe_run`: приоритет
  вне диапазона; рекурсивный мьютекс: владелец с нулевым счётчиком; watchdog:
  испорченный таймаут);
- ветви watchdog для незарегистрированного процесса — до них тест не доходит
  из‑за дефекта N3.

Мутационное тестирование
------------------------

Покрытие показывает, какой код выполнялся, но не показывает, проверяется ли
его результат. `mutate.py` вносит в каждую выполненную строку по одной мелкой
ошибке (оператор, константа, условие, удалённая инструкция или критическая
секция), собирает тесты и смотрит, заметил ли её хоть один.

```sh
test/unit/coverage.sh --dump-covered=/tmp/covered.txt
python3 test/unit/mutate.py --covered /tmp/covered.txt --work /tmp/mut \
        --fuzz-seeds 30 --report /tmp/mut.txt
# выжившие — ещё раз, под санитайзерами
python3 test/unit/mutate.py --covered /tmp/covered.txt --work /tmp/mut \
        --retest /tmp/mut.txt.json --report /tmp/mut-san.txt \
        --cxxflags "-fsanitize=address,undefined -fno-sanitize-recover=undefined"
```

Полный прогон — около 40 минут на двух ядрах. Последние результаты: в первом
прогоне из 714 компилируемых мутантов убито 567 (79,4%); после добавления
тестов повторный прогон выживших убил ещё 70, итого около 89%. Оба прогона
сделаны до последних добавлений (проверки состояния прерываний, `atomic`,
новые тесты round‑robin), итоговый прогон на текущем наборе ещё не выполнен.

Часть мутантов не может быть убита в принципе:

- критические секции в `*_isr`‑функциях: в порте обработчики не вкладываются;
- эквивалентные изменения (`<=` вместо `<` в выборе минимума, повторное
  обнуление таймаута, `DUMMY_INSTR()`);
- код, скрытый известным дефектом (тело `try_pop_back` — N1, `put_off` — N8);
- сохранение указателя стека в `context_switch_hook`: в порте он постоянен;
- защитные остановки (`launch_precheck`, проверка порчи таймаута в watchdog).

Как писать тест
---------------

Тело `UT_TEST` — это подготовка. Оно выполняется до `OS::run()`, назначает тела
процессам P0…P4 (P0 — старший), обработчики прерываний и итоговую проверку.
Тест завершается, когда вернулись все назначенные тела. Таймер тикает, только
когда все процессы заблокированы (из процесса IDLE), или явно через
`ut::tick()`.

```cpp
UT_TEST(mutex, contended_lock_blocks_until_unlock)
{
    static OS::TMutex M;
    ut::proc(0, []{ OS::sleep(1); ut::trace("P0-lock"); M.lock(); ut::trace("P0-got@%u", ut::ticks()); M.unlock(); });
    ut::proc(1, []{ M.lock(); OS::sleep(5); ut::trace("P1-unlock"); M.unlock(); ut::trace("P1"); });
    ut::at_end([]{ CHECK_TRACE("P0-lock P1-unlock P0-got@5 P1"); });
}
```

- Лямбды не захватывают переменные: общее состояние — `static` внутри теста.
- `ut::proc(i, body, ut::DAEMON)` — процесс, завершения которого тест не ждёт;
  `ut::SUSPENDED` (только P4) — процесс стартует приостановленным.
- `ut::irq(n, handler)` и `ut::raise(n)` — пользовательские прерывания 0…7;
  обработчик начинается с `OS::TISRW isr;`.
- `ut::on_systimer()`, `ut::on_context_switch()` — хуки ядра; `ut::max_ticks()` —
  предел времени (по умолчанию 2000 тиков).
- `ut::on_critsect_exit(hook)` — вызов при каждом выходе из внешней критической
  секции; `ut::seed()` — seed запуска; `ut::async_ticks(period_us)` — системный
  таймер от настоящего таймера (недетерминированно, только для стресс‑тестов).
- `get_interrupt_state()` возвращает 1, если прерывания сейчас запрещены.
- `UT_TEST_SUSPENDED` — тест процесса `pssSuspended`; в конфигурации с таблицей
  масок он считается тестом дефекта 3.
- Тест без процессов — обычный юнит‑тест, ядро для него не запускается.
- Каждый тест выполняется в отдельном процессе Linux (`fork`): зависание
  (таймаут 5 с) или падение одного теста не влияет на остальные.
- Внутри тестов пишите `OS::sleep()`, а не `sleep()`: иначе вызов конфликтует
  с `sleep()` из libc.
